ProcessPuzzle Base Workflow Backend is the server-side companion of [`@processpuzzle/base-workflow`](../../js-shared/base-workflow-frontend/README.md). It provides the building blocks for defining, executing, and monitoring long-running business workflows in a Spring Boot application. It builds on top of [`base-state-backend`](../base-state-backend/README.md).

## Technologies

- **Java 25**
- **Spring Boot 4**
- **Project Lombok**
- **Maven** for build and dependency management
- **Nx** for monorepo task execution

## Architecture

Hexagonal, following ProcessPuzzle's convention (`adapters/inbound`, `adapters/outbound`, `usecases/inbound`, `usecases/outbound`, `domain`), split into two layers under `com.processpuzzle.workflow`:

- **`definition`** — design-time authoring, split the way SPEM splits Method Content from Workflow (see `api-contracts/src/main/resources/SPEM-Concept.md`). `RoleDefinition`, `ArtifactDefinition`, `TaskDefinition` and `ToolDefinition` are a tenant-level *catalog*: each is a standalone aggregate keyed by `(orgKey, id)`, authored once through its own CRUD resource, and composed into any number of workflows. They reference each other by plain id — a role is `responsibleFor` artifact ids, a task names role ids and artifact ids — which is what lets the authoring UI render each reference as a `RELATED_ENTITIES` control over the referenced entity's own list.

  A `Workflow` *uses* them: its `roles`, `artifacts`, `tools` and `tasks` hold `RoleUse` / `ArtifactUse` / `ToolUse` / `TaskUse` objects, each naming a definition by id plus whatever is true of it only in that workflow. `TaskUse` is the one with content today — which of a task's permitted roles performs it here, what it waits for (`dependsOn`), how that wait is satisfied (`joinType`), whether it may run alongside its siblings (`parallel`), and which state it expects each input in and leaves each output in (`artifactStates` — recorded and drawn, not yet enforced). `ArtifactUse` carries an optional `objectName`, the modeler's `new_order : Order`. `RoleUse` and `ToolUse` are a definition id and nothing else, deliberately: a use is an object rather than a bare string so that per-workflow configuration can be added later without changing the shape of the reference list. There is no `WorkflowUse` and no `WorkflowDefinition` — a workflow is not reused inside another one, it is `extends`-ed, which is a different relation.

  `Workflow.startEvents` say how an instance comes into being (an input artifact reaching a state, a triggering event, a manual launch by an authorized role, or a time-based precondition). Each is one flat value with a `startType` discriminant rather than a subtype per mechanism, which is how every ProcessPuzzle contract models a variant and what keeps it a plain Jackson round-trip in its JSONB column. `StartEventAdmission` enforces the two mechanisms an explicit `POST /instances` can satisfy — roles through the host's `StartAuthorizationPort`, the input artifact's state through `EntityStateGateway` — and answers 403 when no event admits the start, 409 when the workflow only starts on its own. A `TRIGGERING_EVENT` start does start it on its own: `TriggeredStartListener` observes base-event's `DefinedEventOccurred` (a shared event — this module does not depend on base-event) and calls `StartWorkflowInstanceUseCase.startTriggered`, which bypasses admission, maps the event into the initial context with `payloadMapping`, and skips a subject that already has a running instance. The `eventType` is checked against the catalog at save time through `EventCatalogPort`, which the host application supplies; see `SPEM-Concept.md`.

  `Workflow.events` are its intermediate events: `EventUse`s naming a catalogued event, a `direction` (THROW or CATCH), and the same `dependsOn` / `joinType` wiring a task has — tasks and events name each other, and the validator refuses an id collision with a task or start event and any cycle. A MESSAGE needs a `correlationKey`; a THROW may not name a SYSTEM event. Both kind rules apply only when `EventCatalogPort.kindOf` can tell the kind. A catch may wait for a `timer` (`TimerDefinition`: DURATION, DATE or CYCLE, an ISO literal or a `$.` context path, read by `TimerExpressions`) instead of a catalogued event, and with `attachedTo` it is a boundary event of a task, `interrupting` or not. Every save, import and delete publishes `WorkflowChangedEvent`, on which the execution layer reschedules the workflow's start timers.

  `WorkflowValidator` enforces referential integrity when a workflow is *saved* — every use resolves, every `performedBy` is a role both the workflow and the task allow, every artifact a task touches is declared. The catalog delete guards (`DeleteRoleDefinitionUseCase` and siblings, over `CatalogReferenceScanner`) are the other half of the same invariant. `ResolveWorkflowUseCase` pairs the two halves back up for the execution layer, refusing a dangling reference rather than resolving around it.
- **`execution`** — runtime interpretation of a workflow: `WorkflowInstance`, `TaskInstance`, `ArtifactInstance` are three *independent* aggregates (not one nested tree) so that completing unrelated parallel tasks never contends on a shared optimistic lock. `TaskActivationService` is the engine: it decides which PENDING/BLOCKED tasks become ACTIVE after every state change, honoring `dependsOn`, `joinType` and the `parallel` flag, and reaches the intermediate events now due — an `EventInstance` beside each `TaskInstance`. A THROW publishes `EventThrown` (shared; base-event turns it into `DefinedEventOccurred`) and counts as done at once, so activation runs to a fixed point; a CATCH starts WAITING. `IntermediateCatchListener` delivers an occurred event — SYSTEM by subject, MESSAGE to one correlated catch, SIGNAL to all — through `OccurCatchEventUseCase`, which folds the catch's payload mapping into the context the way a task's contribution is. `WorkflowProgression` is the shared tail of completing, skipping and catching: activate, then lock the instance row and close it if every task and event is terminal.

  Timers are polled, not scheduled: a reached timer catch waits with a `dueAt`, and `TimerSweep` — run every `base-workflow.timers.interval` (default `PT30S`) by `TimerSweepScheduler`, off with `base-workflow.timers.enabled: false` — fires each due row in its own transaction through `FireTimerUseCase`, which publishes `TimerFiredEvent` and re-arms a CYCLE. A boundary event is armed when its task becomes ACTIVE and cancelled when the task ends; `CatchOccurrence`, shared by timers and delivered events, cancels the task of an interrupting one. The engine's dead-path elimination then cancels what can no longer be reached (`TaskInstanceStatus.CANCELLED`, which is terminal but satisfies nothing). The same sweep fires `StartTimerSchedule` rows — one per TIME_BASED_PRECONDITION start event, kept in step by `StartTimerScheduleReconciler` — through `FireStartTimerUseCase` and `StartWorkflowInstanceUseCase.startScheduled`. `InputArtifactStartListener` starts an INPUT_ARTIFACT workflow when the shared `PlatformEvent` says its subject reached the required state. An instance is a snapshot: it keeps the task ids and artifact names it was born with, so a later edit to a shared catalog entry does not rewrite a workflow already in flight.

Per the API contract, base-workflow is a pure orchestrator: rule evaluation is delegated to base-rule (`rule :: usecase`), state machine transitions to base-state (`basestate :: domain`) — the only two feature modules this one is allowed to depend on, and only through their published named interfaces. It never depends on base-entity or base-artifact directly (neither exposes one yet); instead it defines outbound ports (`RoleMembershipPort`, `StartAuthorizationPort`) that the host application implements, the same pattern base-app-backend uses for `OrganizationAccessPolicy`.

## Known gaps

- **No `base-workflow-events.yaml` contract exists yet.** The events in `execution.events` are this module's own best-effort design of what other modules would plausibly need to hear about (workflow/task lifecycle, artifact creation), not a negotiated shared schema. Revisit their shape once one exists.
- **No inbound listener from base-state.** `ArtifactInstance.currentState` is never refreshed after creation — base-state doesn't yet expose an instance-level event to listen for (it's still a scaffold). `ArtifactInstanceCreatedEvent` is the first half of that integration; the second half (a listener that updates `currentState`) doesn't exist yet.
- **An unmatched message is dropped.** A MESSAGE that no catch is waiting for when it arrives is logged and discarded — there is no buffer, so a catch reached a moment later waits for the next one.
- **A catch cannot be occurred or skipped by hand.** There is no endpoint to complete a waiting catch or skip it; cancelling the instance is the only way out of a wait nobody will answer.
- **A triggered start is deduplicated by subject, not by occurrence.** `startTriggered` skips a subject with a running instance of the workflow, so a second, genuinely new occurrence for the same subject is ignored while the first run is still going.
- **Deleting a catalogued event is not refused.** base-event deletes an `EventDefinition` a workflow's start or intermediate event still names; the workflow then never starts, or throws into a void and waits forever.
- **Task completion never drives an entity's state.** `TaskCompletionStateTriggerListener` listens to `execution.domain.TaskCompletedEvent`, which nothing publishes — `CompleteTaskUseCase` publishes `execution.events.TaskCompletedEvent`, which carries no trigger. Re-pointing the listener would not help: no `completionStateTriggerKey` exists on `TaskDefinition`, `TaskUse` or the contract, and `TaskPreconditionEvaluator` (`preconditionStateKey`) is never called. The intended direction now that `TaskUse.artifactStates` exist: an output state *is* the target — completing the task asks base-state for the transition into it, so no separate trigger key is needed — and an input state is the activation precondition. Still open: which entity instance an ENTITY artifact binds to (the instance's `entityId`, or one per artifact instance), and how it squares with base-state being the sole writer of the state attribute.
- **Tool step input/output mapping is a placeholder.** `StepDefinition.inputMapping`/`outputMapping` are documented as PPCL expressions / JSONPath, but base-workflow doesn't own an expression engine. `ToolStepExecutor` currently does direct top-level key lookups only.
- **Old columns and tables linger after the Definition/Use split.** Roles, artifacts and tasks used to be JPA children of the workflow row and are now their own tables; `ArtifactDefinition.type`/`entityTypeId` are now `artifactType`/`artifactTypeId`; a workflow's reference lists changed from id arrays to `...Use` objects. With `ddl-auto: update` none of that is dropped or migrated — an existing database keeps its rows and needs the seed file re-imported, or the columns moved by hand. The table name is still `workflow_definition` for the same reason: renaming it would orphan the existing table rather than migrate it.
- **Only this module's PUTs honour a client-supplied version.** The five `*Input` schemas carry an optional `version`; supply the one you read and a stale write is refused with 409 instead of silently overwriting a concurrent edit. base-rule, base-state and base-document keep `version` on the read schema only and rely on Hibernate's `@Version` detected at flush — which catches two genuinely overlapping transactions but not the ordinary case of a form loaded minutes ago, because each request loads the row fresh inside its own transaction and so has nothing stale to detect. Worth lifting to the other modules; the shape to copy is `WorkflowDefinitionMapper`'s `version` pass-through plus the existing guard in each replace use case.
- **The frontend has not been migrated.** `base-workflow-frontend`'s hand-written mappers and descriptors still mirror the pre-split contract (typed `TaskIOReference` inputs, bare-id reference lists, no start condition), so the authoring UI will not round-trip against these endpoints until it is updated.
- **A start that cannot start is not retried.** A triggered or input-artifact start whose workflow cannot start is logged and dropped: the listener completes, so the publication registry considers it delivered.
- **A time-based start's milestone and precondition are not evaluated.** `milestoneRef` and `preconditionExpression` are recorded; only the `timer` starts the workflow.
- **A timer path that does not resolve leaves the timer unarmed.** A `$.` expression whose variable is missing, or holds something that is not a time, is logged and the catch waits without a due time — only cancelling the instance releases it.
- **Timers are as late as the sweep.** `TimerSweep` runs every `base-workflow.timers.interval` (30s), so a timer fires up to that much after it is due, and a sweep that falls behind fires a burst. Missed firings of a start timer's cycle (a restart, say) are skipped, not caught up.
- **Start timers are deduplicated by optimistic locking only.** With several replicas each sweep fires the same due schedule row; the row's version makes all but one roll back, which is correct but wasteful. There is no leader election.
- **The REST resource is still called a workflow.** Paths, `operationId`s and OpenAPI tags say `workflows`/`workflowId` — and so, following the generated API interfaces, do the endpoint classes — while the schemas and domain classes say `Workflow`. Deliberate, to keep the frontend working through the rename; worth finishing in one commit alongside the frontend migration.
