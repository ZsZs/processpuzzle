# ProcessPuzzle Business Starters — Design

## 1. Goal

A **Business Starter** is an official, tested and complete configuration of the platform for one business
problem (inventory, billing, organising a sail race, ...). It is a bundle of YAML definitions: Entity, State,
Rule, Widget, Document, Workflow and App.

- A business developer starts from a starter instead of an empty organization.
- Later, independent developers offer their own starters in a **Business Starter Marketplace**, in the spirit
  of the IntelliJ plugin marketplace. This document covers the **official route** only.
- All starters are free for now.

A starter is **not** the same as exporting and importing an organization's definitions through a local file.
That is a separate, later feature with its own trust rules (§9).

## 2. Properties of a starter

| Property | Manifest field | Notes |
|---|---|---|
| Unique id | `id` | kebab-case slug, immutable. Provenance and the catalog key on it. |
| Name | `name` | Display name; may change and be translated. |
| Description | `description` | |
| Version | `version` | semver. A published version is immutable. |
| Author | `author` | `ProcessPuzzle` for official starters. |
| License | `license` | SPDX identifier, or `proprietary`. |
| Definition YAMLs | `contents` | Existing seed YAML formats, see decision 7.4. |
| Migration script | `migration` | Placeholder; form to be decided together with upgrades (§8). |

Compatibility fields: `definitionSchemaVersion` and `platform.minVersion`. Catalog fields: `category`, `tags`,
`icon`, `locales`. Full sketch: `starter-manifest.example.yaml`.

A starter is **all or nothing**: no dependencies between starters, no partial install, no sample data.
Sample data that demonstrates a starter lives in the Testbed instead.

> **Decision 11 (2026-11-19) changes what a starter is:** a starter is a *domain* starter — the definitions and
> modules of one business domain, never an application shell — and an organization may install several. Sections
> 4, 6 and 7 below describe what is built today (manifest v1); the target design and the plan are in §11.

## 3. Layers

| Layer | Responsibility | Where |
|---|---|---|
| Authoring | Write, review and version starters | Git, `processpuzzle-biz/business-starters/<id>/` |
| Distribution | Validated, immutable bundles + catalog index | CI → MinIO bucket `processpuzzle-starters` |
| Catalog read API | List starters and versions; tenant-free | `base-starter-backend` (`GET /starters...`) |
| Catalog UI (marketing) | Browse starters | `processpuzzle-biz-frontend`, reads `catalog.json` directly |
| Install | Fetch a bundle by reference, replace one org's definitions | `base-starter-backend` + `base-starter-frontend`, orgKey-scoped |
| Applied-starter record | Which starter an org started from | SeedJob (`starter_id`) in `PROCESSPUZZLE_ADMIN`; `starter_installed` in the org's backend |

## 4. Authoring and release

```
processpuzzle-biz/
  business-starters/
    sail-race-organizer/
      manifest.yaml
      entities/  states/  rules/  widgets/  documents/  workflows/  modules/  apps/
      translations/  assets/
      icons/
      migrations/   (placeholder)
```

One folder per starter; the version lives in `manifest.yaml`, and old versions live in git history and in the
bucket. Starters follow the **same release process as the source code** (conventional commits, release
branches, CI → stage → prod). Per released starter version CI:

1. runs `tools/business-starters/package-starters.mjs` against the bucket's current `catalog.json`. It checks
   each manifest and the files it lists, writes the integrity hashes into the packaged manifest, zips
   `bundle.zip` deterministically, and merges `catalog.json`. A version already in the catalog is skipped when
   its bundle is byte-identical and refused when it is not (immutability: changed content needs a new version);
2. **dry-run installs every new bundle into an empty organization** of a running backend — a starter that
   cannot be imported never reaches the bucket;
3. uploads the new `<id>/<version>/` folders, then `catalog.json` last, so the index never names a missing zip.

## 5. Bucket layout — the registry

The registry **is** the bucket. There is no registry table.

```
processpuzzle-starters/
  catalog.json                       # generated by CI: every starter, every version
  <id>/<version>/bundle.zip
  <id>/<version>/entry.json          # manifest summary + sha256 of bundle.zip + publishedAt + status
  <id>/icon.svg
```

`catalog.json` is `{ catalogVersion: 1, starters: [{ id, name, description, author, license, category, tags,
icon, versions: [{ version, publishedAt, status, definitionSchemaVersion, sha256, bundle }] }] }` — a superset
of what the Biz frontend's `starter-catalog.ts` reads. `status` is `published`, `deprecated` or `yanked`. A yanked version disappears from the catalog but stays in
the bucket, so organizations that applied it are not broken. Status changes are commits, published by CI.

Why a bucket rather than a database table:

- MinIO is the one store every stack already shares. Every candidate database misfits: Biz has no
  persistence, Admin is VPN-restricted, Testbed is reset daily, and a table per stack would make CI publish
  into every backend of every environment.
- CI writes once and needs no running backend and no service account per backend.
- The bundle and its registry entry are uploaded together, so the index cannot announce a missing zip.
- Trade-offs: queries run in memory (fine for dozens of starters), and edits go through CI, not a UI.
  When the marketplace needs third-party uploads, reviews or payments, a database is introduced then and
  filled from the bucket.

Access: the bucket is **publicly readable, writable only by CI**. The Biz frontend reads `catalog.json` and
the icons through its NgInx (`/starters/` → MinIO), so Biz needs no backend code for the catalog. Every
environment's MinIO has its own bucket, filled by that environment's release.

## 6. API (base-starter-backend)

Tenant-free catalog, served from the bucket index:

| Endpoint | Purpose |
|---|---|
| `GET /starters` | Catalog: published and deprecated starters, filtered to those this platform can import |
| `GET /starters/{starterId}` | One starter with its installable versions, newest first |

Organization-scoped install:

| Endpoint | Purpose |
|---|---|
| `GET /organizations/{orgKey}/starters` | The starter applied to this org, with provenance |
| `POST /organizations/{orgKey}/starters/install` | Body `{ starterId, version, dryRun }`. The backend fetches the bundle from the bucket and verifies its sha256 — bytes never pass through a client. |

The existing byte-based `POST /organizations/{orgKey}/definitions/import` stays as the internal entry point
the install calls. It is no longer exposed to users until local file import exists (§9).

Two callers, one per stack that installs:

1. **Subscription** (Custom). Biz sends the `starterId` with the sign-up to Admin, which stores it on the
   organization's SeedJob. The SeedJob's data step passes it to the customer's Custom backend, and Custom
   installs it. **Zero or one starter per subscription.** If the install fails the organization is seeded
   without a starter and the failure is recorded on the SeedJob.
2. **Designer** (Custom, Testbed). "Install starter" from the catalog, dry-run preview first.

## 7. Importer rules

- **Order:** Entity, State, Rule, Widget, Document, Workflow, Module, Translation, App, Asset.
- **Modules and the app:** a `modules/` file is a YAML document with a `moduleDefinitions:` list and an `apps/`
  file one with an `appDefinitions:` list — the entries of the bundled default-apps files. Modules are released as
  they are imported and the app is published, so the installed application is live at once. An organization has one
  application and sign-up creates it empty, as `app`: a starter whose app is `app` replaces it, one with another id
  removes the placeholder while it is untouched, and a starter without an app leaves a fresh empty one.
- **Translations and assets:** the files a module or an app brings along are listed under `translations` and
  `assets`, and the path says whose they are: `<dir>/modules/<module key>/<path>` or `<dir>/apps/<app id>/<path>`
  (`assets/apps/app/cards/plan-race.svg` is the app file `app:cards/plan-race.svg`; `assets/modules/plan-race/docs/guide.md`
  is `module:docs/guide.md`). They are written through the use cases a designer's upload uses, so the same path, size
  and count rules hold, and the module's text rules too: a translation is `translations/modules/<key>/<locale>.json` and
  holds the texts the module authors (its name and route titles) and the texts its widgets name under the module's
  transloco scope — the module key with its dashes written as underscores (`conduct-race` is `conduct_race`) — all keyed
  relative to that scope, so `participant.title` is read as `conduct_race.participant.title`. An application's texts are `translations/apps/<app id>/<locale>.json`: the texts of its own pages,
  such as a home page's cards, under whatever keys its widgets name (letters, digits, `_`, `-` and `.`), so nothing is
  checked against the definition. An owner the bundle does not define refuses the install as well. Each file is
  released as it is stored, so the running application serves it at once. A bundle file is capped like every other
  (`base-starter.bundle.max-file-bytes`, 1 MiB).
  Reinstalling removes the previous files first, like every definition.
- **Atomic:** schema and cross-reference validation before any write; all writes in one transaction.
- **Replace, all or nothing:** installing a starter deletes the organization's existing definitions and
  imports the starter's. This is allowed **only while the organization holds no entity objects and no
  workflow instances**; otherwise the install is refused (409). The install never deletes instance data, and
  there is deliberately no "reset organization" that would (decision 10). The dry-run report lists what would
  be deleted as well as what would be created.
- **Provenance:** every imported definition is tagged with `starterId`, `starterVersion` and a content hash,
  so "untouched" can later be told apart from "customized" — the basis for upgrades (§8).
- **Schema versioning:** `definitionSchemaVersion` lets the importer migrate or reject old bundles.
- **Trust:** the bundle's sha256 must match its registry entry; size limits and path checks still apply.
- **Dry run:** the same transaction, rolled back.

## 8. Decisions

1. **Catalog API in `base-starter-backend`, catalog data in MinIO** (2026-10-06, replaces the 2026-10-05
   decision that put the catalog endpoints in Biz). The catalog is tenant-free; the library stays in the
   `processpuzzle` repo because Testbed and Custom both need it. Biz reads `catalog.json` directly.
2. **New library pair.** Orchestration in `base-starter-backend`, install UI in `base-starter-frontend`.
3. **No compile edges.** `base-starter-backend` depends on no feature library. `processpuzzle-core` declares
   the `DefinitionImportParticipant` SPI; each feature implements it for its own definitions.
4. **Bundle files use the existing seed YAML formats** (`DefaultEntitiesDocument` and its siblings).
5. **One transaction** across participants — valid while all modules share one DataSource.
6. **Provenance in one importer-owned table**, keyed by `(orgKey, kind, key)`. Feature tables are unchanged.
7. **Entity definitions and objects are organization-scoped.** Global types (`_global`) remain open, including
   whether a starter may ship one.
8. **All or nothing** (2026-10-06): no `requires`, no partial install, no conflict strategies, no sample data.
   Still holds *per starter*; decision 11 allows several starters per organization.
9. **Replace only into an empty organization** (2026-10-06): see §7. Superseded by decision 11: an install
   adds to the organization, and only replaces the definitions of the same starter.
10. **One application per organization** (2026-10-11). An organization is one tenant, runs one starter and
    holds one subscription; there is no second isolation key for "applications" inside a tenant. A customer
    who wants a second application takes a second subscription and gets a second organization. Changing the
    starter of an organization that already holds data stays refused (409) — no reset that deletes instance
    data. Nothing in Admin links several organizations to one customer yet; that is added only when asked
    for. Decision 11 keeps one application per organization but drops "runs one starter".
11. **Domain starters, several per organization** (2026-11-19). A starter that ships an application overwrote
    the customer's own header, footer, sidenav and home page, and the last installed starter won. A starter
    therefore carries only domain content — entities, states, rules, widgets, documents, workflows, modules, their
    translations and assets, and its common — and never an application. The application belongs to the customer:
    sign-up seeds a platform default shell, and an install mounts the starter's modules into the customer's app
    from **mount hints** in the manifest. Rejected: two starter kinds (application and domain starters), because
    an application starter is mostly branding, which is the customer's, and it would still collide with the
    domain starters it bundles. Sub-decisions:
    - **Mounting goes to the draft** (11a). An install releases the starter's own definitions, but adds its mounts
      to the app's *draft* only, so the customer's unreleased app changes are never released by an install. The
      customer releases the app. Exception: an app that has never been changed from the default shell (seed,
      starter choice at sign-up) is released at once, so a new subscriber sees a running application.
    - **Collisions are refused** (11b). Keys of all kinds share one namespace per organization. An install whose
      keys collide with another starter's or the customer's own definitions is refused (409, listed in the dry-run
      report); keys are never rewritten. Official starters follow a **key-prefix convention** (§11.2), and CI
      checks every official starter against every other.
    - **Existing applications stay as they are** (11c). Organizations that installed a v1 starter keep their
      application; it is the customer's from then on and is never replaced by an upgrade.

Postponed:

- **Upgrades.** The intent is regular automatic upgrades. Needs the migration-script format and a policy for
  customized definitions; provenance already records what is needed.
- **Install counts.** Derived from the Subscriptions in Admin.
- **Third-party starters**, signing, reviews, paid starters.

## 9. Not starters: local export/import

Exporting an organization's definitions to a file and importing such a file is useful but separate: the
content is not official, not tested and fully untrusted. It reuses the byte-based importer later, under its own
design. Exports never go into the `processpuzzle-starters` bucket.

## 10. Status and next steps

Done (2026-10-06), in `processpuzzle`:

- Manifest: `author`, `license`, `migration`; `requires`, `conflictsWith`, `seedData` and `install` removed.
- Importer: replace-only. The SPI gained `DefinitionImportParticipant.removeAll` and `InstanceDataProbe`
  (base-entity: entity objects, base-workflow: workflow instances); the additive path is gone.
- Catalog read model over the bucket (`HttpStarterRegistry`), `GET /starters…` and `POST …/starters/install`.
- Designer screen installs from the catalog instead of uploading a file.
- `processpuzzle-starters` bucket in the infrastructure compose: public-read, plus an optional
  `starter-publisher` MinIO account (`MINIO_STARTER_PUBLISHER_PASSWORD`) that may write only that bucket.
- The packager, `tools/business-starters/package-starters.mjs`.

Next:

1. CI publishing in `processpuzzle-biz`: run the packager, the dry-run gate, the upload; set the publisher
   password in the stage and prod infrastructure env files; NgInx `/starters/` route for the Biz frontend.
2. One pilot starter (e.g. inventory) end to end: commit → CI → bucket → Designer install.
3. Subscription: starter choice in Biz, field on Admin's SeedJob, reference passed in the seed call,
   Custom installs it and reports the outcome. Implemented in `processpuzzle-biz` (PR #73, 2026-10-11);
   end-to-end check on stage pending.
4. **Delete guards per definition.** With decision 10 the only way to empty an organization is to delete
   its data and definitions by hand, so a definition must not be deletable while data or other definitions
   still depend on it. Today (audit 2026-10-11) only entity definitions (objects of the type), workflows
   (ACTIVE / SUSPENDED instances only) and workflow catalog items (references) refuse. Missing: attribute
   removal (TODO in `DeleteAttributeUseCase`, though the API promises 409), state machines, rules bound to an
   entity, widgets, documents, apps, events, and every cross-feature reference (attribute `linkedEntityType`,
   state machine and rule bound to an entity, workflow artifacts naming an entity / state machine / document,
   apps naming widgets / documents). There are no FK constraints to fall back on — cross-feature references
   are plain strings. Direction: add a keyed `count(orgKey, kind, key)` to `InstanceDataProbe` plus a
   reference-probe SPI, so the importer's org-wide gate and the per-definition guards share one mechanism.
   Align the workflow rule with the importer's (finished instances count too). The frontend deletes without
   confirmation and does not show the 409; fix that alongside.

## 11. Domain starters — target design and plan (decision 11)

### 11.1 What changes

| Aspect | Manifest v1 (today) | Manifest v2 (target) |
|---|---|---|
| Content | Definitions, modules **and an app** | Definitions and modules; no `apps/`, no `translations/apps/**`, no `assets/apps/**` |
| Per organization | Zero or one starter | Zero or more starters |
| Install | Replaces every definition of the org; only into an org without data | Adds this starter's definitions, or replaces its own (reinstall, upgrade); others untouched |
| Data gate | Org-wide: no entity objects, no workflow instances | Per starter: no objects of *this starter's* entity types, no instances of *its* workflows |
| Uninstall | None | `DELETE /organizations/{orgKey}/starters/{starterId}`, same per-starter data gate |
| Application | Starter's app replaces the placeholder `app` | Sign-up seeds a default shell; install adds mounts to the app's draft (11a) |
| Common membership | One common per org | One common per installed starter that has one |

v1 bundles stay installable, the v1 way, until SailRC 1.0.0 is published; then v1 is refused.

### 11.2 Key-prefix convention

Every key a starter defines — entity codes, state machines, rules, widgets, documents, workflows, events, module
keys and so also transloco scopes — starts with a short prefix the manifest declares (`keyPrefix: sailrc`), for
example `sailrc-race`, module `sailrc-plan-race`, scope `sailrc_plan_race`. The packager refuses a v2 bundle with a
key outside its prefix, and a prefix already taken by another starter in the catalog. Customer-authored keys are
not checked against the convention; a collision with them is refused at install (11b).

### 11.3 Mount hints

```yaml
mounts:
  - moduleKey: sailrc-plan-race
    basePath: plan-race          # suggestion; on a taken path the mount is skipped and reported
    nav: { icon: event, labelKey: nav.title }          # relative to the module's transloco scope
    launcher:                                          # card on the default shell's home page
      image: module:launcher.svg
      titleKey: launcher.title
      subtitleKey: launcher.subtitle
      contentKeys: [launcher.content]
      link: overview
```

Hints are data, not app definitions: the install turns them into a `ModuleMount` and a nav item in the app's
draft. The customer may move or remove them; a reinstall does not re-add what the customer removed (the mount's
provenance records that it came from the starter). The texts and the image are the module's, so a module carries
everything it needs to appear in any application.

### 11.4 Default shell and `module-launcher`

Sign-up seeds the organization's `app` as a platform default shell: logo, title and the account widgets in the
header, a sidenav filled from the mounts' nav items, the version button in the footer, and a `home` route holding
one `module-launcher` widget. `module-launcher` renders a card per mounted module from that module's launcher hint,
in mount order — today's SailRC home page, without the starter owning it. It is an ordinary widget: a customer may
use it on any page, or replace the home page altogether.

### 11.5 Plan

| Phase | Where | Content |
|---|---|---|
| 1. Manifest v2 | core: packager, manifest schema | `manifestVersion: 2`, `keyPrefix`, `mounts`; refuses app content and keys outside the prefix; catalog-wide prefix uniqueness. |
| 2. Additive importer | `base-starter-backend`, SPI | Install scoped by provenance `starterId`; collision check against all definitions of the org (dry-run report lists them); per-starter data gate through a keyed `InstanceDataProbe.count(orgKey, kind, key)` — the same probe as the delete guards (§10 item 4); uninstall endpoint; `GET …/starters` returns a list; `starter_installed` holds one row per starter. |
| 3. App integration | `base-app` backend + frontend | Mount merge into the draft (11a, with the untouched-shell exception); default shell seed; `module-launcher` widget; sidenav items from mounts. |
| 4. Commons | core, `base-starter-backend`, base-entity | `DataSpaceDirectory.commonsOf(orgKey)` instead of `commonOf`; a shared type resolves to the common of the starter that defines it; reserved codes checked against all of the org's commons (the prefix convention keeps them apart). |
| 5. Sign-up, Admin, Designer | processpuzzle-biz | Sign-up multi-select; SeedJob `starter_ids[]`, installed one by one, failures recorded per starter; Designer lists installed starters with install, reinstall and uninstall. |
| 6. SailRC 1.0.0 | processpuzzle-biz `business-starters/` | Prefix `sailrc`; drop `apps/`; home cards become launcher hints with module assets and texts; the app's nav texts move into the modules. Existing stage organizations keep their app (11c). |
| 7. CI gate | `publish-business-starters.yml` | Dry-run each bundle into an org with the default shell, then all official starters into one org, to catch collisions. Rework the gate for commons at the same time (a common bundle is rolled out first, not dry-run as a tenant). |

Phases 1–3 make domain starters usable; 4–7 follow independently.
